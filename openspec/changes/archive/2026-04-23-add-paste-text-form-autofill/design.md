## Context

当前插件能够扫描 Ant Design 表单字段并执行填充，但主要输入是结构化 `FillData`。新需求是用户直接粘贴一段微信聊天式文本，让系统自动完成字段映射和填充。目标页面字段包含文本框、封闭选项、联动字段（如产品名称 -> 资金方）以及四级级联分类（问题类型&分类）。

该场景具有三个约束：一是文本噪声高、结构不稳定；二是业务字段存在高风险误填点（尤其手机号与分类叶子）；三是用户接受“填不满手动补”，不接受“错填”。

## Goals / Non-Goals

**Goals:**
- 支持从单段自由文本抽取候选信息并映射到已扫描表单字段。
- 在手机号、封闭选项、联动字段上实现可解释的确定性规则，并默认保守停填。
- 在“问题类型&分类”上实现合法树约束下的分层决策，支持停在 1~4 任意层级。
- 与现有 `SCAN_FORM -> FILL_FORM` 链路兼容，最小化对原有填充执行器的侵入。

**Non-Goals:**
- 不在本次引入 OCR、附件自动上传、跨页面多表单拼接。
- 不追求所有字段满填；低置信字段保留为空。
- 不在本次引入独立模型训练或在线学习闭环，仅保留规则与少样本可扩展位。

## Decisions

### 决策 1：新增“文本映射前置层”，复用现有填充执行链路
- 方案：在背景脚本新增“粘贴文本 -> 候选槽位 -> 字段映射 -> FillData”流程，输出仍为 `FillData`，最终复用现有内容脚本填充器。
- 理由：不重写底层 DOM 填充逻辑，降低改动面与回归风险。
- 备选方案：直接在 content 端边解析边填充。未采纳，因为会耦合 UI 文本处理与 DOM 操作，难以测试和回放。

### 决策 2：手机号采用硬规则优先，覆盖“单号双填”
- 方案：若仅识别到 1 个手机号，则同时填 `来电号码` 与 `注册号码`；识别到多号时按语义优先填 `来电号码`，`注册号码`在低置信时可留空。
- 理由：该规则来自业务明确确认，且能显著降低漏填。
- 备选方案：一律只填来电号码。未采纳，因为会降低常见场景完成度。

### 决策 3：封闭选项统一“命中才填”，联动字段分两阶段执行
- 方案：`工单来源`、`端口`、`产品名称`、`资金方`等仅在选项命中时填充。联动字段先填产品，再等待联动渲染后尝试资金方。
- 理由：封闭选项误填成本高，且资金方依赖上游字段出现，必须顺序化。
- 备选方案：对未命中值使用随机或首项兜底。未采纳，因为违反“宁可不填，不可错填”。

### 决策 4：问题类型&分类使用“域路由 + 分层停靠”
- 方案：先路由到目标分类树（默认主域，必要时切商城/车抵贷等子域），再逐层选择 L1->L4；每层独立置信判定，低置信即停层，不强选下层。
- 理由：合法树规模大且存在同名分支，必须在父子约束内选择；分层停靠符合业务策略。
- 备选方案：一次性输出四级完整路径。未采纳，因为叶子误判率高，无法满足保守策略。

### 决策 5：输出“填充建议结果”，明确自动/留空字段
- 方案：在执行填充前形成映射结果对象（含字段值、是否自动填、停填原因），用于 UI 呈现与后续追踪。
- 理由：便于人工快速补录和问题定位，同时不要求向终端用户展示模型解释链。
- 备选方案：静默直接填。未采纳，因为无法定位错漏与迭代规则。

## Risks / Trade-offs

- [分类树多域且节点命名相近] -> 先做域路由与父子合法性校验，路由不稳时仅填高层。
- [聊天文本包含多个手机号，语义冲突] -> 多号场景优先来电号码，注册号码低置信留空。
- [联动字段渲染时序不稳定] -> 产品填充后增加显式等待与重扫，超时后跳过资金方并记录原因。
- [规则覆盖不足导致漏填] -> 以低误填为优先，允许漏填；后续用新样本迭代词典与阈值。
- [页面控件配置差异导致停层行为不一致] -> 按页面真实 Cascader 能力执行，若不支持中间层取值则停在可提交的最高层。
